## 1. 为什么旧签名失效 —— About 对话框的判定被移除

### 1.1 字符串层面：`"Trial"` 被删了

About 对话框的字符串簇（两版对照，偏移均以各自文件为准）：

| b8 偏移 | b8 内容 | b15 偏移 | b15 内容 |
| --- | --- | --- | --- |
| 0x294640 | `%s%s` | 0x295440 | `%s%s` |
| 0x294648 | **`Full`** | 0x295448 | **`Full`** |
| 0x294650 | **`Trial`** | 0x295450 | **`nLst`** ← Trial 消失，nLst 顶上来 |
| 0x294658 | `nLst` | 0x295458 | `%b/%d/%Y` |
| 0x294660 | `%b/%d/%Y` | 0x295464 | `nExpDt` |
| 0x29466C | `nExpDt` | 0x295470 | `SOFTWARE\Internet Download Manager` |

b8 里 `Full`/`Trial` 相邻 8 字节（`46 75 6c 6c 00 00 00 00 54 72 69 61 6c 00`），这是旧签名的核心前提。
b15 里这个 8 字节相邻关系**不复存在** —— 全镜像只剩另外两处 `Full`（标题格式串 `Full\0%s Trial\0` 与 `Full\0\0\0 Trial\0`），都不是 About 的判定串。

### 1.2 代码层面：判定整段被删

同一位置两版反汇编（VA 恰好都在 0x4039xx 附近）：

```asm
; ---- b8 @0x4039CD ----
0x004039CD  lea   ecx, [ebp - 0x18]
0x004039D0  cmp   dword ptr [0x779CDC], ebx     ; ← 标志判定
0x004039D6  je    0x4039DF
0x004039D8  push  0x695E50                      ; "Trial"
0x004039DD  jmp   0x4039E4
0x004039DF  push  0x695E48                      ; "Full"
0x004039E4  call  0x403060

; ---- b15 @0x4039C9 ----
0x004039C9  mov   byte ptr [ebp - 4], 9
0x004039CD  push  0x696E48                      ; "Full"  ← 无条件，没有 cmp
0x004039D2  lea   ecx, [ebp - 0x18]
0x004039D5  call  0x403060
```

**结论：这是一次针对性的反破解改动** —— 作者把「版本行显示 Trial 还是 Full」这个最直观的破解锚点抹掉了，
所以基于它的特征码自然失效。注意 `"Full"` 在 b15 中全镜像**只有 1 处引用**（`push 0x696E48` @ `0x4039CD`），
即「关于」永远显示 Full，**它已经不能再用来判断注册状态**。

## 2. 新标志定位的完整证据链

既然 About 不可用，改用**注册逻辑本身的形状**。三条互相独立的锚点：

### 锚点 A1 —— 序列号格式校验 → 写标志

b8 的 `FUN_00450AE0` 在通过「序列号长度 23 且第 5/11/17 位是 `-`」的校验后，把标志写 0。
这个形状是 `cmp eax,0x17` + 三个 `cmp byte ptr [ebp+disp32], 0x2d` + `mov dword [flag], 0`。

```asm
; ---- b8 @0x450D90 ----                        ; ---- b15 @0x450BA9 ----
0x00450D90  cmp  eax, 0x17                      0x00450BA9  cmp  eax, 0x17
0x00450D95  cmp  byte [ebp+0x3f1], 0x2d         0x00450BAE  cmp  byte [ebp+...], 0x2d
0x00450D9E  cmp  byte [ebp+0x3f7], 0x2d         0x00450BB7  cmp  byte [ebp+...], 0x2d
0x00450DA7  cmp  byte [ebp+0x3fd], 0x2d         0x00450BC0  cmp  byte [ebp+...], 0x2d
0x00450DB0  mov  dword ptr [0x779CDC], 0        0x00450BC9  mov  dword ptr [0x77BD24], 0
```

**⇒ b15 标志 = `0x77BD24`**（b8 = `0x779CDC`）。

### 锚点 A2 —— 试用弹窗门控

b8 的 `FUN_005BD440`（下载编号分配器）里 `cmp [flag],0 / je` 后面紧跟 `push 0x14D8`：

```
b8  0x005BD4EA  cmp dword ptr [0x779CDC], 0 ; 74 1D ; ... push 0x14D8 @+0x15
b15 0x005BE1EA  cmp dword ptr [0x77BD24], 0 ; 74 1D ; ... push 0x14D8 @+0x15
```

**试用弹窗的命令 ID `0x14D8` 跨版本不变**，所以这个锚点很稳。**⇒ b15 标志 = `0x77BD24`**。

### 锚点 A3 —— 试用天数阈值重算（最强）

这段把标志映射成「Trial→30 / Registered→15」并存进 `flag+4`：

```
; b8  @0x44CC27
A1 DC 9C 77 00     mov  eax, [0x779CDC]      ; 标志
F7 D8              neg  eax
1B C0              sbb  eax, eax
83 E0 0F           and  eax, 0xF
83 C0 0F           add  eax, 0xF
A3 E0 9C 77 00     mov  [0x779CE0], eax      ; 阈值全局 = 标志+4

; b15 @0x44CCF7  —— 指令序列逐字节相同，只有地址不同
A1 24 BD 77 00     mov  eax, [0x77BD24]
F7 D8 1B C0 83 E0 0F 83 C0 0F
A3 28 BD 77 00     mov  [0x77BD28], eax
```

`neg/sbb/and 0xF/add 0xF` 是一个无分支的「0→15、非0→30」选择器。
这个序列极独特，且**同时给出标志地址与 `标志+4` 的关系**（可自校验）。
**⇒ b15 标志 = `0x77BD24`，阈值全局 = `0x77BD28`**（b8 对应 `0x779CE0`）。

### 2.1 三锚点投票结果（实跑）

## 3. 旁证：写点仍然只有「都写 0」的两处

对标志地址做全 `.text` 引用扫描并按操作码分类：

| | b8 (`0x779CDC`) | b15 (`0x77BD24`) |
| --- | --- | --- |
| 写点 | **2** | **2** |
| └ 写点 1 | `0x450DB2` `mov dword [flag], 0` | `0x450BCB` `mov dword [flag], 0` |
| └ 写点 2 | `0x523A72` `mov dword [flag], 0` | `0x523782` `mov dword [flag], 0` |
| 读点 | 43 | 41 |

**两版都不存在任何把标志写成非 0 的指令** ⇒ 状态机仍然单调，**P1 的语义（初值 1=Trial → 改 0=Full）在 b15 上完全成立**。

进一步交叉验证：两版的 `cmp [flag],0 / je` 站点集合**一一对应**（同样的 7 处，同样的顺序）：

另外 b8 有 2 处 About 相关的标志读点（`0x403685`、`0x4039D2`），b15 只剩 `0x403685` 一处 ——

## 4. 新的版本无关签名（建议实现）

**核心思想：从「界面上看得见的 Trial/Full」转向「注册逻辑本身的形状」，并做多锚点投票。**

```python
def find_registration_flag(pe):
    votes = {}   # flag_va -> [anchor names]
    for name, fn in (("threshold", _a_threshold),
                     ("serial",    _a_serial),
                     ("naggate",   _a_naggate)):
        va = fn(pe)
        if va:
            votes.setdefault(va, []).append(name)
    # 取票数最高且唯一者；平票则放弃（失败即安全）
    ...
```

三个锚点各自的判据：

| 锚点 | 字节形状 | 为什么稳 |
| --- | --- | --- |
| `_a_threshold` | `A1 <F> F7 D8 1B C0 83 E0 0F 83 C0 0F A3 <F+4>` | 12 条固定指令的无分支选择器，极独特；**自带 F 与 F+4 的自校验** |
| `_a_serial` | `83 F8 17` + ≥3×`80 BD <disp32> 2D` + `C7 05 <F> 00 00 00 00` | 直接给出标志地址；绑定序列号格式校验（核心功能） |
| `_a_naggate` | `83 3D <F> 00 74` + 24 字节内出现 `68 D8 14 00 00` | **命令 ID `0x14D8` 跨 b8/b15 不变**，是最稳的魔数 |

**为什么比旧签名稳：**

1. **旧签名依赖 UI 文案**，作者一改界面（b15 就改了）就失效；新签名依赖**注册逻辑与消息常量**，
   改这些等于改功能本身，成本高得多。
2. **旧签名是单点判据**，找不到就没辙；新签名**三路独立投票**，任一可用即可定位，
   且多路一致时置信度极高（本次两版均 3/3）。
3. **旧签名需要「往回扫」找 `cmp`**（依赖相对布局）；新签名中 A1 直接给出标志地址，
   A3 还额外给出 `F+4` 用于自校验，**不依赖相对布局**。
4. **失败即安全**：票数分散/为零时返回 `None`，工具跳过该补丁而不是猜着改。

## 6. 附带发现：P2 / P3 在 b15 上的状态

虽然不是本任务范围，但既然查了，一并报告（**未修改任何工具**）：

### P2（到期显示 9999）—— 仍然可用

`%b/%d/%Y` 在 b15 中**仍然唯一**，位于 VA `0x00696E58`（b8: `0x00695E60`），
后面有 3 字节 NUL 填充，足够容纳 `%b/%d/9999`（11 字节）。

### P3（弹窗函数置空）—— 仍然可用，但**锚点链断了一环**

- b15 弹窗文案 `This is 30 day trial version…` 在 VA `0x006AD3B0`（b8: `0x006AC330`），唯一。
- 其 CString 全局 = `0x0078A924`（b8: `0x00788904`）。
- **但 b15 里弹窗函数不是以 `mov eax,[该全局]` 开头的**，所以现有 P3 实现里的
  `find_all(b"\xA1"+global)` 这一步会返回 0 处，导致 P3 被跳过（这正是 b15 上 P3 报
  「没找到 mov eax,[该 CString]」的原因）。
- 实际 b15 弹窗函数入口 = **VA `0x0047D4D0`**，第一条指令确实是 `A1 24 A9 78 00`
  （`mov eax,[0x78A924]`），前面有 **5 字节** `int3` 填充（b8 是 9 字节）。
- 其收尾 `mov eax,1 ; ret` 在函数内 **+0x3D**（与 b8 的 +0x3D **完全相同**），
  因此补丁字节也是**同样的 `E9 38 00 00 00`**。

> 给 Lead 的提示：P3 的定位链在 b15 上需要放宽 —— 建议把「唯一性要求」从
> 「`mov eax,[global]` 恰好 1 处」改为「在该全局的所有引用中，找落在 `.text` 且
> 前面紧跟 `int3` 填充、且函数体内含 `B8 01 00 00 00 C3` 收尾的那一处」。
> 这样 b8/b15 都能命中，且不会因引用数变化而误判。
